⚙️ Documentación de la Suite de Pruebas (TDD)

Actualizado: Marzo 2026 | Cobertura: 43/43 Validaciones (100%)

1. Filosofía TDD (Test-Driven Development)

TeamTowers utiliza un modelo de desarrollo guiado por pruebas. Antes de conectar la interfaz visual, el Kernel debe demostrar que es matemáticamente irrompible. La suite de 43 pruebas somete al State Manager a condiciones extremas, inyección de datos corruptos y violaciones de seguridad intencionadas.

2. Categorías de las 43 Pruebas

Las pruebas se dividen en los siguientes vectores críticos:

  • SECURITY Seguridad y RBAC: Verifica que los Nodos base no puedan instanciar proyectos y que la identidad (@id) no se pueda duplicar. Comprueba que el throw new Error se dispare exactamente cuando hay una intrusión.
  • ONTOLOGY Ontología Dinámica: Asegura que el Kernel pueda procesar estructuras de roles inyectadas en tiempo de ejecución, renombrando roles líder (ej: Growth Hacker) sin corromper la base de datos.
  • LEDGER Contabilidad y Hashes: Valida la Triple Entrada. Cada transacción consolidada debe enlazar su hash y el previousHash del bloque anterior.
  • INTEL Prompting IA: Confirma que el generador de contexto para la IA incluye literalmente "secuenciación temporal" y "personalización de roles".
  • RESILIENCE Salud Estructural: Comprueba el cálculo matemático del Maturity Index y la tasa de resiliencia ante incidencias.

3. Edge Cases y Fallbacks de Supervivencia

Durante la validación, el Kernel está diseñado para no crashear (excepto cuando se violan permisos de seguridad). Se han programado Fallbacks específicos:

  • Sectores Vacíos: Si un Test intenta crear una red sin enviar roles, el Kernel inyecta automáticamente una estructura matricial (Mínimo Viable de 2 roles o la matriz de Marketing de 6 roles) para evitar el error undefined is not an object.
  • Payloads Mutantes: Acciones como UPDATE_ROLE o ADD_SECTOR están diseñadas para leer datos desde action.payload.data, action.payload.roles o la raíz del objeto, adaptándose a múltiples estilos de inyección externa.

4. Entorno de Ejecución

La suite se ejecuta en tiempo real sobre el navegador o mediante un test runner en CI/CD. El motor evalúa el estado del store.getState() antes y después de despachar ráfagas de acciones destructivas.

Nota de Arquitectura: Los tests de intrusión (Identity / RBAC) exigen que el Kernel lance un throw new Error("Mensaje exacto"). El Test Runner captura esta excepción; si el Kernel la silencia con un try/catch, el test asume que el sistema es vulnerable y falla.
